## Commands

```bash
kache daemon             # status
kache daemon start       # background process; waits for readiness
kache daemon stop        # requests drain and waits for ownership release
kache daemon restart     # service-manager restart or manual replacement
kache daemon run         # foreground process
kache daemon log         # follow logs
```

Use `KACHE_LOG=kache=debug kache daemon run` for foreground debugging.

When an installed service manages this cache, `start` and `restart` start the service instead of spawning a process. On macOS, kache loads the job with `launchctl bootstrap` if launchd no longer has it.

On Linux, `daemon log` follows the systemd journal only. A daemon started without the service logs to `<runtime_dir>/daemon.log` and `<cache_dir>/kache.log`.

On Unix, a daemon that a build starts runs in its own session, so Ctrl-C in the build's terminal does not stop it. On Windows, a daemon started under Cargo stays in Cargo's job object and stops when the build is interrupted. Install the service to avoid that.

## Install a login service

```bash
kache daemon install
```

On macOS this installs `~/Library/LaunchAgents/ninja.kunobi.kache.plist`. On Linux it installs and enables the `kache.service` systemd user unit. On Windows it registers the Task Scheduler task `kache-daemon`, which runs `kache daemon run` at logon.

Remove either service with:

```bash
kache daemon uninstall
```

On current macOS releases, the first connection to a LAN cache endpoint may ask for Local Network permission. If an older service installation reports `No route to host`, reinstall it with the current Kache binary.

## Updates and config changes

The daemon records the running binary's build epoch. A newer client asks an older daemon to drain and exit. The service manager restarts installed services; otherwise later background work starts a fresh daemon.

The daemon also fingerprints the active config file and restarts after it changes. `kache daemon start` and automatic starts drop the remote settings from the environment (`KACHE_S3_BUCKET`, `KACHE_S3_ENDPOINT`, `KACHE_S3_REGION`, `KACHE_S3_PREFIX`, `KACHE_S3_PROFILE`, `KACHE_S3_USER_AGENT`, `KACHE_LOCAL_ONLY`, `KACHE_REMOTE_READONLY`), so put the remote in the config file. Other environment is fixed when the process starts. An installed service uses its stored environment. To try remote variables from a shell, run `kache daemon run` in the foreground.

## Shared lifecycle

Kache uses `kunobi-daemon` for process locks, verified readiness, request drain,
and exclusive replacement. The old daemon releases its cache resources before
the replacement starts. A startup timeout cannot report “Background cache:
running” or authorize killing unfinished work.

An installed service owns only its configured runtime directory. A command using
another cache instance starts that instance independently. Lock files remain on
disk after shutdown; deleting them can split ownership between two processes.

New daemons advertise a separate Protobuf control endpoint. It authenticates the
OS peer and checks the Kache service identity and cache-instance identity. Older
daemons retain the bounded legacy health/shutdown exchange. Failed binary
negotiation never falls back to that legacy exchange.

Kache retains cache compatibility, upload persistence, service installation and
compiler fallback policy. Accepted upload intents survive shutdown in the spool;
the shared crate neither owns nor cancels those jobs. Consumers also decide how
to export the shared lifecycle observations.

## Idle shutdown

The default idle timeout is disabled:

```toml
[cache]
daemon_idle_timeout_secs = 600
```

The equivalent environment variable is `KACHE_DAEMON_IDLE_TIMEOUT`. A later build can start the daemon again.

## Offline behavior

When the daemon cannot be reached:

- local hits and local stores continue
- exact remote checks and prefetch are skipped
- validated upload intents remain in `<cache_dir>/upload-queue`
- a later daemon replays queued uploads before retiring their files

The monitor falls back to direct store and event-log reads. Check `kache daemon log` when it remains offline.

If the daemon fails to start, `kache daemon status` names the file that holds the reason: `<runtime_dir>/daemon.log` for `daemon start` and automatic starts, `~/Library/Logs/kache/err.log` under launchd, and `journalctl --user -u kache.service` under systemd. The Windows task keeps no startup output, so run `kache daemon run` to see the error.
