## Several Cargo builds at once

Kache is a compiler wrapper, not a build frontend. Keep running `cargo`. Give each live build its own `CARGO_TARGET_DIR` so Cargo's fingerprints stay isolated.

Worktrees that share one target directory can run `kache cargo -- build` or `kache cargo -- check` instead: on Cargo 1.91 or newer it keeps each worktree's intermediate build state in that worktree's own `target/`, and final artifacts still go to the shared directory. Other Cargo commands, commands with `--config`, `-C` or `-Z`, and projects that already set a build directory keep Cargo's own layout.

After a local and remote miss, the wrapper joins a machine-wide flight for its cache key, then takes a memory-weighted permit before the per-key build lock. A unit that [adaptive incremental mode](/docs/getting-started/quick-start#executables-and-incremental-builds) seeds after those misses takes a permit too, without the flight; the incremental compiles that follow skip the cache and take none. Only compiles with the same key wait for each other. Two build scripts, two versions of a crate, or two `parser.c` files from different grammars compile in parallel. Warm predictions and passthroughs skip discovery coordination. An eligible Rust unit without a valid input prediction first waits for a peer discovering the same invocation, then validates the resulting prediction and computes its own key. A peer that seeds the unit ends that wait before it compiles, since a seed stores no entry and records no prediction. Sources and environment remain local; only dependency paths beneath Cargo target directories can share an identity.

The permit pool size is `std::thread::available_parallelism()`, with a floor of 1. Unmeasured compiles occupy one slot. Unmeasured rustc invocations that run the system linker (binaries, dylibs, cdylibs, and proc macros) occupy two. A library compile is not a link, even though Cargo asks it to emit `link`. On Unix, a real compile records the child's peak RSS by crate name. Later invocations of that crate occupy `ceil(rss / slot)` slots, clamped to the pool. A slot is the machine's memory divided by the pool size, and never less than 512 MiB. On Linux the memory is the smaller of physical memory and the cgroup's `memory.max`. Where the memory cannot be read, a slot is 512 MiB.

The memory estimate cannot see what else is running: builds outside Kache, an editor, a browser. So the scheduler also checks whether the machine is short of memory. Under memory pressure ordinary admission asks for the whole pool, waiting for other compiles to finish. Recovery admission is bounded separately below. Slots held by running tests still count against the ordinary request, so a test waiting on a compile cannot stall it. On macOS, pressure is the kernel's pressure level at warning or critical. On Linux it is memory PSI, some task stalled on memory for at least 10% of the last ten seconds, read from the process's cgroup when it has its own `memory.pressure` and from the host otherwise. Other systems report no pressure. Set `cache.scheduler_memory_pressure = false` or `KACHE_SCHEDULER_MEMORY_PRESSURE=0` to turn the check off.

Compiles and test binaries that wait for slots queue for them, across every build that shares the cache directory: worktrees, separate target directories, and test runs. Requests are served in the order they arrived, except that a request from a foreground build is placed 10 seconds ahead of one from a background build. A request keeps its place while later ones arrive, so a background request that has waited 10 seconds goes before any foreground request that comes after it. A background build is one running at Darwin background priority (`taskpolicy -b`) on macOS, a positive nice value, `SCHED_BATCH` or `SCHED_IDLE` on Linux, or the idle or below-normal priority class on Windows. A request the daemon executes takes the priority of the build that sent it. A compile that is already running keeps its slots whatever its priority. When the first request in line needs more slots than are free, smaller requests behind it can use the free slots, but only as many times as the pool has slots. After that the free slots are saved for the first request until it fits. A test saves only test slots, and a compile counts the slots saved for a test like slots running tests hold, so a heavy compile can still run in the reserve. A request that is cancelled or killed loses its place at once. A waiter that has not been able to run for two seconds, such as a background process the OS has starved of CPU, is skipped until it runs again.

Kache releases before this queue take free slots without queuing. Their running compiles still count against the pool, but while releases are mixed on one machine an older wrapper can take slots a queued request was saving up. A request whose ordinary capacity wait reaches its limit leaves the queue and uses recovery admission, described below, which does not queue.

Compiler invocations share a 30-minute allowance for ordinary coordination waits,
including dependency discovery, a peer compiling the same key and permit
acquisition. Each phase spends the allowance left by earlier phases. Each
ordinary capacity wait is also capped at 30 seconds. Compiler runtime and key
computation do not spend the allowance. A compile-first result is stored without
asking for another compiler permit.

When ordinary capacity admission reaches its limit, one compile at a time can use
recovery capacity. Recovery adds at most two weighted slots to the regular pool,
or one on a single-slot pool. A heavier compile still needs regular slots for
the rest of its weight. Recovery uses the measured or default compile weight;
it does not inflate the request to the whole pool under pressure. Other waiters
continue checking ordinary capacity and wait for the recovery holder to finish.
That additional wait can exceed the ordinary wait limit and remains cancellable. A
holder exiting releases its locks, including after a crash.

If neither ordinary nor recovery admission can obtain capacity before the shared
coordination allowance expires, compilation continues without a permit. The same
fallback applies when the scheduler directory cannot be used. Set
`KACHE_SCHEDULER=0` or `[cache] scheduler = false` to turn the
scheduler off. Test-runner lease waits keep their own limits.

Two cargo processes that miss the same crate still share one real compile when the first stores an entry the second can restore. Distinct target directories remain required.

## Daemon pipelines

Daemon request admission and compiler scheduling are different limits.
`cache.daemon_execution_concurrency` controls concurrent cache pipelines, using
CPU count and, on Unix, descriptor headroom by default. It does not set the
number of compilers allowed to run. Change it in the daemon's startup settings
and restart the daemon. Compiler permits remain memory-weighted as described
above.

## Several test runs at once

Test binaries can wait for the same pool. Set `kache test-runner` as Cargo's target runner and each test binary takes slots until it exits. A quarter of the pool, at least one slot, stays reserved for compiles. Builds started inside a running test use that test's slots. See [Test runner](/docs/getting-started/configuration#test-runner) to turn it on.
