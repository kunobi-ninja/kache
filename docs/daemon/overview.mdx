title: Daemon overview
description: What the background daemon owns and what still works without it
---

The daemon keeps network and maintenance work away from compiler processes. Local cache lookup and storage do not require it.

## Responsibilities

- Download an exact entry after a local miss.
- Store completed C/C++ compiles handed over by wrappers.
- Upload newly stored entries in the background.
- Replay durable upload intents after a restart.
- Prefetch likely entries at the start of a build session.
- Refresh the remote key index used by fallback planning.
- Run garbage collection at startup and every six hours, including `[cache.volumes]` shards.
- Flush entries that were stored without an fsync, every two seconds.
- At the start of a build, copy large executables next to the paths their restore will write, so the restore only renames the copy into place.
- Compact `index.db` when the machine is quiet.

With `cache.daemon_publish` enabled (the default), a C/C++ wrapper can hand its private output snapshots to the daemon. The compiler still runs in the wrapper. If the daemon cannot accept the work within 25 ms, the wrapper keeps the local publication path. A compile whose store is a `[cache.volumes]` shard always stores from the wrapper.

Report JSON marks daemon publication attempts with `store_handed_off` and records their background time in `daemon_store_ms`. That time is separate from the wrapper's `store_ms`. A daemon crash can lose queued cache entries; the compiler outputs remain available to the build.

Set `cache.prefetch_enabled = false` or `KACHE_PREFETCH_ENABLED=0` to disable speculative prefetch while retaining exact remote checks and uploads.

The daemon lists an S3 remote only with `cache.remote_key_listing = true`, which needs `s3:ListBucket`. A filesystem remote is listed unless the setting is `false`. It keeps an index of remote keys that the planner uses for crates that no build manifest, shard or local history covers. If the remote refuses to list, the daemon stops listing and logs one warning.

## When it is required

Local-only caching works with no daemon. A configured remote needs the daemon for reads, writes, and prefetch. If the daemon is unavailable, the wrapper continues with the local store and compiles an exact remote miss locally.

## Endpoint placement

On Unix the default socket is `<runtime_dir>/daemon.sock`. Windows derives a named-pipe identity from the configured path. Override the runtime root with `KACHE_RUNTIME_DIR` or only the endpoint with an absolute `KACHE_SOCKET_PATH`.

The daemon also binds a lifecycle control endpoint next to the socket: the socket path with its extension replaced by `.ctl`. With the default `daemon.sock` it is one byte shorter than the socket. A custom `KACHE_SOCKET_PATH` without an extension gets a longer one.

Use a short, user-owned runtime directory. Unix socket paths are limited to 103 bytes on macOS and 107 on Linux. `kache daemon start` checks both endpoint paths against that limit and refuses to start a daemon when either is too long. Shared temporary directories also allow another local user to interfere with adjacent lock and state files.

Every client and daemon process must resolve the same runtime and socket settings. Installed services do not inherit later shell exports; put persistent values in the config or service definition.

## Basic commands

```bash
kache daemon start
kache daemon status
kache daemon log
kache daemon stop
```

Bare `kache daemon` is an alias for `kache daemon status`.

See [Lifecycle](/docs/daemon/lifecycle) for service installation and restart behavior.
