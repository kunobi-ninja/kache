## Several Cargo builds at once

Kache is a compiler wrapper, not a build frontend. Keep running `cargo`. Give each live build its own `CARGO_TARGET_DIR` (or `kache cargo`) so Cargo's fingerprints stay isolated.

After a local and remote miss, the wrapper joins a machine-wide flight for its cache key, then takes a memory-weighted permit before the per-key build lock. Only compiles with the same key wait for each other. Two build scripts, two versions of a crate, or two `parser.c` files from different grammars compile in parallel. Warm predictions and passthroughs skip discovery coordination. An eligible Rust unit without a valid input prediction first waits for a peer discovering the same invocation, then validates the resulting prediction and computes its own key. Sources and environment remain local; only dependency paths beneath Cargo target directories can share an identity.

The permit pool size is `std::thread::available_parallelism()`, with a floor of 1. Unmeasured compiles occupy one slot. Unmeasured rustc invocations that run the system linker (binaries, dylibs, cdylibs, and proc macros) occupy two. A library compile is not a link, even though Cargo asks it to emit `link`. On Unix, a real compile records the child's peak RSS by crate name. Later invocations of that crate occupy `ceil(rss / 512 MiB)` slots, clamped to the pool.

If the scheduler directory cannot be used, compilation continues without a permit. Set `KACHE_SCHEDULER=0` or `[cache] scheduler = false` to turn it off.

Two cargo processes that miss the same crate still share one real compile when the first stores an entry the second can restore. Distinct target directories remain required.
