---
title: Cache key
description: Inputs, normalization, and tools for explaining a cache miss
---

Kache hashes the inputs that can change compiler output and normalizes machine-local paths that should not. Missing a real input risks a wrong hit; retaining harmless machine identity causes avoidable misses.

## Rust key inputs

The exact set depends on the invocation. It can include:

- rustc identity and target
- linker identity for outputs that invoke linking
- crate name, crate types, edition, cfg values, and features
- source and included file contents discovered through dep-info
- recorded input-set predictions that substitute for the dep-info spawn on warm builds (`cache.input_predictions`)
- code-generation flags, rustflags, and requested emit kinds
- the contents of `--extern` dependencies
- compile-time environment values rustc reports
- native libc version and hashed CRT/startup objects for host-loaded Linux outputs
- macOS SDK identity (version and build) for host-loaded Darwin outputs
- configured salt, extra inputs, and declared environment inputs

Host-loaded Linux and macOS links pass through if those runtime inputs cannot be resolved, rather than sharing a binary neither host pinned. rustc-bundled self-contained WebAssembly targets (`wasm32-unknown-unknown`, the WASI family, `wasm32v1-none`, `wasm64-unknown-unknown`) are cached; custom target specs, emscripten, and `link-self-contained=no` pass through.

On macOS, a cached debug link gets ld64 `-oso_prefix` for `--out-dir`, so `N_OSO` object paths in the binary are not checkout-local.

Incremental directory names and harmless local path spellings are excluded or normalized.

The live implementation is the authority. Use `kache why-miss` and trace logging to see the components for a particular build.

Input predictions are enabled by default for eligible Rust units. Kache
revalidates their recorded inputs and falls back to dependency discovery when
the record cannot be used. Set `KACHE_INPUT_PREDICTIONS=0` or
`[cache] input_predictions = false` to disable predictions.

### Clippy

`cargo clippy` runs workspace crates through `clippy-driver`, which Cargo
composes with Kache as `kache clippy-driver rustc …`. Kache keys those units
like any rustc unit and adds the Clippy version, the package's `Cargo.toml`
(the `cargo` lint group reads it), the `.clippy.toml` or `clippy.toml` Clippy
would load (found from `CLIPPY_CONF_DIR` or the crate's manifest directory
upwards, keyed by content), and the lint arguments Cargo passes in
`CLIPPY_ARGS`. A hit restores the outputs and replays the recorded
diagnostics, so warnings appear exactly as on the first run. Other
`RUSTC_WORKSPACE_WRAPPER` drivers stay uncached.

### Misses without a record

The first time a unit is built on a machine, Kache has no recorded closure to
derive a key from. When no remote could hold the entry either, the miss is
certain, so instead of spawning `rustc --emit=dep-info` to discover the
closure before compiling, Kache compiles first and keys from the dep-info the
compile emitted. Every input in that closure is checked against the build's
start time; an input written during the compile leaves the result unstored.
Peers of the same unit in other target directories wait for this compile as
they would for a pre-pass. `[cache] deferred_discovery = false` restores the
pre-pass.

A C or C++ compile without a recorded read set does the same: it compiles
with a dependency file and keys from the digest of the files that compile
read, instead of preprocessing first. A record whose files changed is
rediscovered with the preprocessor, which yields the same key.

## Path normalization

Kache maps known roots to stable sentinels before hashing and asks the compiler to emit matching remapped paths. This allows equivalent worktrees and runners to share entries.

Common mappings include the workspace, Cargo home, Rustup home, temporary directory, target directory, and configured base directories. Add a missing root with `KACHE_BASE_DIR` or `paths.base_dirs`.

Do not choose an overly broad base directory. Normalization deliberately merges path identities; two genuinely different inputs must not map to the same sentinel.

Disable Rust path normalization for a local profiling or debugging session:

```bash
KACHE_RUSTC_PATH_NORMALIZE=0 cargo build
```

That puts real paths in debug information and makes the key local to those path identities. C/C++ has the corresponding `KACHE_CC_PATH_NORMALIZE=0` control.

Coverage-instrumented Rust builds use real paths and a separate, path-local key namespace so coverage tools can find source files.

Crates that trybuild builds under `target/tests/trybuild/` get the same treatment. trybuild passes `--cfg trybuild` to every one of them and compares rustc's rendered diagnostics against the checked-in `.stderr` snapshots after substituting the real crate, workspace, and registry directories, so a remapped path such as `/kache/home/...` or `/proc/self/cwd/...` would fail every snapshot. Those units still cache, keyed by their trybuild target directory.

## Debugger source maps

On macOS and Windows, map the stable workspace prefix back to your checkout:

```text title="gdb"
set substitute-path /kache/workspace /absolute/path/to/checkout
```

```text title="lldb"
settings set target.source-map /kache/workspace /absolute/path/to/checkout
```

Linux workspace paths use `/proc/self/cwd` when possible, so running the debugger from the workspace root usually resolves them directly.

## Inputs the compiler does not report

Use these controls only for a real hidden input:

- `cache.key_salt` or `KACHE_KEY_SALT` for an opaque toolchain boundary
- crate `kache.toml` for files read during compilation but absent from dep-info
- `workspace.extra_inputs` for workspace-root provider inputs
- `cache.key_env_vars` for environment read by proc macros through `std::env`
- `cache.path_only_env_vars` for locator variables proven not to affect emitted bytes, and for the `crate:VAR` assertion that keeps a crate whose include comes from another crate's macro (`tonic::include_proto!`, `lalrpop_mod!`) reusable across checkouts

See [Configuration](/docs/getting-started/configuration) for syntax and safety limits.

## Explain a miss

```bash
kache why-miss my_crate
```

The command compares recent key material for that crate and prints changed groups. In a second checkout with no earlier build of the crate, it compares with the same unit built in another checkout. Groups are hashed after path normalization, so the checkout path alone does not change them. The exception is `remap` when path remapping is off: that group keys the checkout path on purpose. Any other group that differs between checkouts is a real input difference or a path that normalization missed. The same key in both checkouts means no key input differs.

For individual components, run the trace command it suggests, typically:

```bash
KACHE_LOG=trace cargo build -p my_crate 2>&1 | grep '\[key:my_crate\]'
```

Warnings also identify residual absolute paths that survive normalization.
