Open the terminal dashboard:

```bash
kache monitor
kache monitor --since 1h
```

Without `--since`, the monitor lists the last hour of builds. The figures on the first screen are the daemon's last 24 hours, the same window as `kache stats`. The monitor attempts to start the daemon for transfer statistics. It still reads the local store and event log if the daemon is unavailable.

## Now

The monitor opens on Now.

| Figure | Meaning |
| --- | --- |
| Store size | Logical output bytes, with the configured store cap under it |
| Hit % | Lookups that hit, over lookups |
| Time saved | Compile time restored from the cache over the last 24 hours |
| Builds | How many builds are in the list below |

The Now size counts logical output bytes. The Store tab shows deduplicated blob bytes, and `kache stats` uses those registered blob bytes for its Cache and Store rows. The cap applies to registered blob bytes.

Under the figures: the share of compile time that came back from the cache, and the share of lookup time that was a miss. Remote is one line. When the daemon reports `not configured` or `local-only`, that line reads `remote is off`.

The list under that shows five builds: name, misses, and time saved. Misses count compiles that missed, including ones whose output was already in the store. A build with no lookups shows `—`. Up and Down move the selection. The list follows the newest build until you move; Home returns to that. Enter opens Why.

## Tabs

1. `Now` is the screen above. The build list is here.
2. `Build` shows the selected build: compiles still running, then that build's compiler events, with outcome, action, timing, and size. A build whose events are all passthroughs and whose crate names were not recorded collapses to one line, and points at another build when one of those has misses. On a tall terminal, a lookup strip covers the last five minutes, or the `--since` window, with hits above misses.
3. `Why` explains the selected build. It leads with the verdict: how many lookups hit, compile time spent on misses, and Kache's overhead as a share of lookup time. Misses are collapsed to their causes, most frequent first: a failed store or a rejected lookup (a caching failure to fix), a dependency cascade named by the crate that actually changed, the crate's own changed inputs, no earlier compile in the loaded history, or unexplained. Each bar is that cause's share of the misses. Passthroughs are grouped by reason, with queries such as `--print` kept apart from compiles. Crates that keep missing across builds of the same tree are listed as chronic. PgUp and PgDn scroll the whole tab.
4. `Projects` lists observed target directories. Each tree shows its size, a bar for local dependencies, and how much of the tree is already cached. Enter shows the other columns: incremental output, build scripts, binaries, fingerprints, and profiles. Press `r` to rescan. A `target` directory is labeled with the project above it. A stale tree is marked `~`.
5. `Store` lists cache entries. The title includes physical blob bytes and the share of logical size that sharing saved. A muted line under the table names the client version, the daemon, the wrapper, and rustc. Press `s` to change sort order.
6. `Transfer` shows recent remote uploads and downloads.

A build is every event sharing one session id. The wrapper records one per workspace, and it covers the crates, build scripts, and C/C++ compiles of that workspace until it sits idle for five minutes, so Cargo commands run back to back count as one build. Events from older wrappers have no id and are grouped by build root with the same five-minute rule. Those builds carry a `~` after their name.

Cascade causes need per-dependency digests on the events, which `[cache] explain_miss = true` records. Without it the Why tab says so. When a crate has no earlier compile in its own tree, the Why tab compares it with its latest build in another build tree, such as another worktree of the project. A cascade is then named by the crate that changed, and that crate shows the input groups that differ. A crate whose inputs match the other tree still reads as having no earlier compile. Every figure on the tab describes the loaded history: with `--since`, a crate whose last compile is before the cutoff reads as having no earlier compile.

`dup` means the compiler ran after a key miss but produced blobs already in the store. It is not a cache hit. A passthrough is not a miss either: Kache never consulted the cache for it.

## Keys

```text
q, Ctrl+C         quit
p                 pause and resume (the log keeps its place; nothing is lost)
Tab, Shift+Tab    next and previous tab
1 2 3 4 5 6       Now, Build, Why, Projects, Store, Transfer
Up / Down, j / k  on Now, Build, and Why: pick a build
                  on Projects: pick a tree
                  elsewhere: scroll one row
Enter             on Now and Build: open Why
                  on Projects: show or hide the other columns
PgUp / PgDn       on Now: move five builds; elsewhere: scroll one page
Home              on Now: follow the newest build again; elsewhere: first row
End               on Now: select the oldest listed build
                  on Build: follow new events again
                  elsewhere: last row
f                 filter Build, Why, or Store
Esc               clear the current filter
s                 change Store sort
c                 clear Build events
r                 rescan Projects
```

The monitor starts by following the top build, and the Now list title says "following the top build". Pressing Up on the first row returns to that mode. The top build is the newest running one, or the newest finished one when nothing is running.

Clicking a tab title selects it. On Now the mouse wheel moves the selected build by three. On the other tabs it scrolls the panel.

Narrow terminals drop the least important columns first instead of clipping every column. Below 60×16 the monitor says so and points at `kache stats`, which prints the same numbers as text and works in a pipe.

## Triage

- Daemon offline: run `kache daemon status` and inspect `kache daemon log`.
- Store near its limit: the daemon evicts entries on its own. If cloned outputs keep entries in place, preview stale targets with `kache clean --stale 14d --dry-run`.
- No remote activity: check daemon state, credentials, and `kache doctor`.
- Unexpected misses: run `kache explain`, or `kache explain <crate>`.
