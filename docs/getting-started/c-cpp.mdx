---
title: C/C++ caching
description: Cache supported GCC, Clang, and clang-cl object compilations
---

Kache caches conservative, single-source C and C++ object compilations. If it cannot prove that an invocation is safe to cache, it runs the real compiler unchanged.

## Cargo build scripts

`kache init` covers both rustc and the objects a build script compiles through the `cc` crate. Without it, put a shim on `PATH`.

On Unix, `kache init` sets `HOST_CC` and `HOST_CXX` in Cargo's config, and `CC_KNOWN_WRAPPER_CUSTOM=kache`. On Windows it sets only `CC_KNOWN_WRAPPER_CUSTOM`, so choose clang-cl through `CC` as shown under [Prefix method](#prefix-method). Init never sets `CC` or `CXX`, so `cargo build --target` keeps the cross compiler the `cc` crate would have found.

PATH shims also cover C code in Cargo builds when the crate invokes `cc` or `gcc` from `PATH` without `HOST_CC`.

## Make, CMake, autotools, PKGBUILD

Run `kache init` to enable C/C++ caching for terminal builds on Unix. It creates compiler links and offers to save the PATH setup for zsh, bash, or fish. It shows the files before changing them and backs up existing files.

```bash
kache init
```

Open a new terminal after setup, or run the activation command printed by init in the current terminal. Then use Make, CMake, or your existing build command. Compiler calls made through `PATH` go through Kache; explicit compiler paths are unchanged. Previously configured CMake build directories may need reconfiguration to select the compiler links.

Use `kache init --no-shell` to leave terminal setup alone while configuring Cargo. For managed dotfiles or another shell, use the manual setup:

```bash
kache init --shims
export PATH="$HOME/.local/lib/kache/shims:$PATH"
```

For `makepkg`, you can set the path directly:

```bash
# ~/.makepkg.conf
PATH="$HOME/.local/lib/kache/shims:$PATH"
```

The APT and AUR packages also install `/usr/lib/kache` with links for the unversioned names:

```bash
export PATH="/usr/lib/kache:$PATH"
```

Nix packages include the same symlinks in `${kache}/shims`, also available at `${kache}/lib/kache`. Add that directory to `PATH` using the [Nix configuration example](/docs/getting-started/installation#nix); no `kache install-shims` step is needed.

The packaged directories hold no versioned compilers such as `clang-19`. `kache init` links those in `~/.local/lib/kache/shims`.

`kache init --shims` creates `cargo`, `cc`, `c++`, `gcc`, `g++`, `clang`, `clang++`, and `rustdoc`. It also links each versioned C and C++ compiler on `PATH`, such as `clang-19`, `clang++-19`, and `gcc-13`. It matches them by name and runs none of them. Keep the real compilers later in `PATH`. When Kache looks for the real compiler it skips any entry that resolves to itself or to a binary named `kache`. It also skips every entry in a directory that holds a `.kache-shims` file. The packages write that file, and `kache init --shims` does when the directory holds only Kache links, so one Kache install on `PATH` never runs another as the compiler. Keep the shim directory for shims only.

After installing another compiler version, run `kache init` again to link it. It does not remove links: after uninstalling a version, delete its link from the shim directory. Until then, that name runs Kache, which reports that no real compiler is behind the shim.

Target-prefixed names (`x86_64-pc-linux-gnu-gcc`) work if you create them by hand or scan `PATH`:

```bash
kache init --shims --from-path
kache init --shims --force
```

Omitting the directory uses `~/.local/lib/kache/shims`. `--from-path` adds a symlink for every compiler-shaped name already on `PATH` that is not Kache itself. `--canonical-only` links only the unversioned names.

Each shim is a native symlink to the `kache` binary. Do not wrap Kache in a shell script; that would spawn a shell per compile.

Kache is a larger process than ccache. On a tree of many tiny `.c` files, measure both before replacing ccache.

`kache doctor` checks the current terminal's PATH and reports the shims as active, broken, installed but not first on PATH, or not installed. If init saved shell setup but doctor still reports inactive shims, open a new terminal or run the activation command. Init cannot change its parent shell's environment.

### Upgrades

The shims link to a path that keeps working after Kache is upgraded. `kache init --shims` checks these in order and uses the first one that reaches the running binary:

1. The installer's alias: Homebrew's `opt/<formula>/bin/kache`, a Nix profile such as `~/.nix-profile/bin/kache`, or mise's `installs/<tool>/latest` (under `MISE_INSTALLS_DIR` when set). The Homebrew and mise aliases must be the installer's symlinks; a copy does not count.
2. The first `kache` on `PATH`, skipping relative entries, version directories (mise and asdf `installs/<version>`, Homebrew kegs, `/nix/store`, pinned Nix generations such as `profile-12-link`), the mise and asdf shim directories, and marked shim directories. A `PATH` entry that is a link into one of those directories is skipped too.
3. The running binary's own path. `kache init --shims` then says to rerun it after each upgrade. asdf installs usually end up here, since asdf keeps no alias for a version.

`kache doctor` shows the chosen path under "Install path", with the installer and whether the path survives an upgrade.

If the binary a shim points at is removed, the shell skips the link and builds run the real compiler uncached. Doctor then reports the farm as broken. Run `kache init --shims` again. In a directory Kache owns (it created it, it carries a `.kache-shims` marker, or it holds only Kache links), a rerun replaces Kache links whose target is missing or not executable, and moves Kache links that point into a version directory to the upgrade-safe path when there is one. It needs no `--force` for either. Links to anything else, and other files, are left alone.

## Prefix method

For a single project that honors `CC` and `CXX`:

```bash
export CC="kache cc"
export CXX="kache c++"
export CC_KNOWN_WRAPPER_CUSTOM=kache
```

The `cc` crate needs `CC_KNOWN_WRAPPER_CUSTOM` so it keeps the real compiler argument. PATH shims do not need that variable, because the compiler name stays `gcc`.

Meson 1.13 and later recognise `kache cc` and `kache c++` in `CC` and `CXX`. Older versions treat `kache` as the compiler, which breaks projects that also build Rust; use the PATH shims there.

For clang-cl driver mode:

```powershell
$env:CC = "kache clang-cl"
```

Windows has no shim generator yet. Use `CC`/`CXX`, or copy `kache.exe` to `gcc.exe` and put that directory first on `PATH`. Create an empty `.kache-shims` file in that directory as well, so another Kache install does not mistake the copies for compilers.

## Cached invocations

Supported shapes compile one source into one object:

```bash
cc -c src/foo.c -o build/foo.o
c++ -c src/foo.cpp -o build/foo.o
clang-cl /c foo.c /Fofoo.obj
```

The key includes the content of the source and of every header the compile reads, the compiler identity, modeled code-generation options, and normalized paths. Header changes therefore invalidate the entry.

Kache learns the read set without a separate preprocessor run. The first time it sees an invocation it compiles right away and asks GCC or Clang for a dependency file alongside the object. A caller's own `-MD` file serves when present. Kache then fingerprints the files the compile read and keys from their digest. Peers compiling the same unit in other build directories wait for that record instead of compiling too. When a record exists but a file in it changed, Kache runs the preprocessor to rediscover the read set. It derives the same key a compile would, so it still finds an entry stored from an earlier state of the tree. A read set that includes a file the assembler opens on its own, or a file modified while the build ran, is compiled and not cached. `KACHE_DEFERRED_DISCOVERY=0` keeps the preprocessor as the discovery on every miss.

Kache recognizes GCC, Clang, Apple Clang, clang-cl, versioned names such as `gcc-13`, and target-prefixed compiler names. It can probe other wrapper names to identify the underlying compiler family.

## Preprocessor memos

Kache remembers each unit's source and header inputs so an unchanged build can derive its key without running the compiler. Identical inputs share one database row, including the local file stamp and the raw and prefix-mapped content hashes. A hit checks the stamp first, then raw content, then mapped content.

A memo names Cargo build directories by role rather than by path: the build script's `OUT_DIR`, the target directory, and the `OUT_DIR` of each crate the unit includes from. Build directories and Cargo commands that give a dependency a different metadata hash, such as `cargo check` and `cargo test`, share one memo per unit.

GC removes memos unused for 30 days and then removes inputs with no references. Successful hits refresh usage at most once a day per memo.

Upgrading from the JSON memo format discards those memos once; units rediscover their inputs on the next build. Compiled artifact entries remain available. SQLite reuses the freed pages. `kache doctor --repair` also compacts a large, sparse index when enough disk space is available; run it after builds finish to avoid lock contention.

## Portability

GCC and Clang entries can be reused across worktrees when source and build paths normalize cleanly. Set `KACHE_BASE_DIR` when the automatic roots do not cover a container mount or out-of-tree layout:

```bash
KACHE_BASE_DIR="$PWD" cmake --build build
```

A configured remote publishes GCC and Clang objects the same way it publishes Rust entries. clang-cl debug objects stay on the machine because CodeView records paths that clang-cl does not remap.

## Passthroughs

Kache currently passes through:

- link and whole-program steps, unless `KACHE_CACHE_CC_LINKS` or `[cache] cache_cc_links` is on
- multi-source or multi-architecture invocations
- response files
- precompiled headers and modules
- coverage and split-DWARF builds
- assembly, including inline `asm` in C, that reads another file with `.incbin` or `.include`
- assembly that uses macros or repetitions (`.macro`, `.irp`, `.irpc`, `.rept`, `.altmacro`) able to generate those directives
- inline `asm` whose text is a computed expression rather than a string literal
- flags it has not classified

The assembler reads `.incbin` and `.include` files after preprocessing, so the key cannot see them, and a computed `asm` string could name one. The three assembly cases run the compiler directly and skip a configured `KACHE_FALLBACK` wrapper, because a wrapper that keys on preprocessor output cannot see those files either.

Inspect passthrough reasons in the monitor or logs:

```bash
kache monitor
KACHE_LOG=kache=debug make
```

You can opt a known-safe flag into the local model:

```toml title=".kache.toml"
[cc]
extra_allowlist_flags = ["-ffunction-sections"]
```

Kache folds the spelling into the key. Do not allow flags whose meaning depends on the host, such as `-march=native`.
